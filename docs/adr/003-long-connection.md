# ADR-003: 长连接优先于 Webhook

**状态**：已接受
**日期**：2026-03-17

---

## 决策

Lynxclaw 的 Channel 接入**默认使用长连接**（Telegram Long Polling / 飞书 WebSocket），Webhook 作为可选备用模式。

## 背景

IM 平台消息接入有两种主流方式：长连接（客户端主动保持连接）和 Webhook（平台推送到公网 URL）。需要在开发体验、部署复杂度和生产可靠性之间做出权衡。

## 考虑的方案

| 方案 | 优势 | 劣势 |
| ---- | ---- | ---- |
| **长连接优先** | 无需公网 IP、无需 SSL 证书、开发调试零配置 | 单点连接、需要重连逻辑 |
| Webhook 优先 | 平台保证推送、天然支持负载均衡 | 需要公网域名、SSL 证书、防重放攻击 |

## 理由

1. **零部署依赖**：长连接无需公网 IP 和 SSL 证书，开发者在本机即可运行，无需 ngrok 或云服务。
2. **飞书官方推荐**：飞书 SDK（lark-oapi）将 WebSocket 长连接作为首选接入方式，文档和示例都以 WebSocket 为主。
3. **Telegram 原生支持**：aiogram `Dispatcher.start_polling()` 开箱即用，无需配置 webhook URL。
4. **防火墙友好**：长连接是出站连接，无需在防火墙上开放入站端口。
5. **简化安全模型**：无需处理 Webhook 签名验证、防重放攻击等安全问题。

## 权衡

- 长连接是单点模式，不能多实例负载均衡（但 Lynxclaw 设计为单机部署，不需要）。
- 需要可靠的重连逻辑（aiogram 和 lark-oapi 都内置了自动重连）。
- 高流量场景下 Webhook 更高效（但 IM Bot 场景下消息频率远未达到瓶颈）。
- 保留 Webhook 作为可选模式（T2.6），供有公网部署需求的用户选择。
